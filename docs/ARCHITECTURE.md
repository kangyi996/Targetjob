# Targetjob 技术架构

## 1. 产品定位

Targetjob 采用受约束的 Agent 工作流，而不是让一个大模型自由地处理所有任务。

系统中的不同职责如下：

| 组件 | 负责内容 |
| --- | --- |
| 确定性程序规则 | 字段校验、权限判断、状态管理和基础数据处理 |
| 大模型 | 自然语言理解、信息提取、任务规划和建议生成 |
| 外部工具 | 搜索岗位、读取代码仓库、解析上传文件和获取其他证据 |
| Agent 编排层 | 根据当前状态决定下一步调用哪个工具或询问用户 |
| 用户界面 | 收集信息、展示过程和呈现结果 |

当前代码已经完成确定性基础，但 Agent 编排层和外部工具仍在后续阶段实现。

## 2. 为什么先选 Streamlit

Streamlit 可以把 Python 函数快速变成网页应用。对于第一版 MVP，它有三个好处：

- 学习成本较低，前端代码量少；
- 可以快速把注意力放在智能体流程和分析结果上；
- 适合面试现场启动和演示。

它不是最终唯一选择。等核心流程稳定后，如果需要更复杂的用户系统、页面交互或多人访问，再考虑拆分前端和后端。

## 4. 当前 MVP 数据流

```text
用户选择身份
      ↓
输入简历 + 职位描述
      ↓
画像字段校验
      ↓
分析器提取关键词并做匹配
      ↓
生成结构化分析结果
      ↓
Streamlit 展示报告
```

## 5. 当前分析器的定位

当前 `targetjob/analyzer.py` 使用可解释的本地规则：

1. 从简历和职位描述中识别预先定义的关键词；
2. 计算两边的交集，作为匹配优势；
3. 计算职位有、简历没有的关键词，作为能力缺口；
4. 根据用户身份附加不同的建议重点。

这样做的目的不是模拟最终的大模型效果，而是先验证完整链路：输入、处理、输出、错误处理和测试都能运行。

## 6. 后续 Agent 接入位置

后续接入大模型时，不会直接删除当前规则分析器，而是在其上增加 Agent 编排层。目标流程是：

```text
CandidateProfile
        ↓
ProfileValidator
        ↓
CareerAgent
   ┌────┼───────────────┬──────────────┐
   ↓    ↓               ↓              ↓
搜索岗位 读取项目证据   匹配分析       模拟面试
```

Agent 每次行动都应该基于结构化状态，并得到结构化结果。它可以选择：

- 继续搜索岗位；
- 追问缺失信息；
- 读取用户提供的项目证据；
- 生成简历建议；
- 开始或继续模拟面试。

## 7. 为什么不让 Agent 负责所有事情

完全交给 Agent 会增加不可预测性、测试难度和运行成本。确定性的规则，例如“团队项目至少需要用户名或个人贡献说明”，应该由程序直接判断。

Agent 更适合处理开放性任务，例如理解用户想找什么工作、决定应该先搜索岗位还是先补充项目证据，以及根据用户回答动态追问。
```

这样网页层不需要知道分析过程是规则、模型还是两者结合，便于逐步升级。
